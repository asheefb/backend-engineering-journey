# Topic 1.3: JVM Internals

## Detailed Notes (Living Document)

These notes cover the concepts studied so far. The JVM layout diagrams
are conceptual; physical implementation varies by JVM and garbage
collector.

## 1. JVM Introduction

The **Java Virtual Machine (JVM)** is a software runtime that loads and
executes Java bytecode.

``` text
Hello.java --javac--> Hello.class (bytecode) --JVM--> Running program
```

-   `javac` compiles `.java` source into `.class` bytecode.
-   The JVM executes bytecode; the original source file is not required
    at runtime.
-   A runtime without the compiler can run already compiled classes.
-   JVM is software, not hardware.
-   Bytecode is portable across compatible JVMs; JVM implementations are
    platform-specific.
-   Compatibility depends on class-file version and runtime APIs.

## 3. Runtime Data Areas

``` text
                 JVM PROCESS
+------------------------------------------------------+
| Shared:                                              |
|  +----------------------+  +----------------------+  |
|  | Heap                 |  | Method Area          |  |
|  | Objects / arrays     |  | Class-level info     |  |
|  +----------------------+  +----------------------+  |
| Per thread:                                          |
|  Thread A                 Thread B                  |
|  +------------------+     +------------------+      |
|  | Java Stack       |     | Java Stack       |      |
|  | PC Register      |     | PC Register      |      |
|  | Native Method    |     | Native Method    |      |
|  | Stack            |     | Stack            |      |
|  +------------------+     +------------------+      |
+------------------------------------------------------+
```

### Heap

-   Shared by application threads.
-   Stores objects and arrays in the usual conceptual JVM model.
-   Garbage collector reclaims objects that are no longer reachable.
-   Becoming eligible for collection does not mean immediate deletion.

### Java Stack

-   Each thread has its own Java stack.
-   Each method call creates a **stack frame**.
-   A frame contains method execution data, including local variables
    and an operand stack.
-   Frames are pushed on calls and popped on returns (LIFO).

``` text
main() -> method1() -> method2()

Thread stack (top)
+------------------+
| method2 frame    |
+------------------+
| method1 frame    |
+------------------+
| main frame       |
+------------------+
```

Deep/unbounded recursion can exhaust a thread's stack and cause
`StackOverflowError`.

### Method Area

Conceptually holds class-level structures such as class metadata,
method/field information and runtime constant-pool data.

**HotSpot nuance:** class metadata is stored in **Metaspace**, which
uses native memory. Do not assume every JVM physically stores all
class-related or static data in one identical location. Static fields
are class-level shared values, but their implementation storage details
differ.

### PC Register

-   Each JVM thread has its own PC register.
-   It tracks the current JVM instruction for that thread.
-   Different threads can be at different instruction positions.
-   Its value is undefined while executing a native method.

### Native Method Stack

Supports native method execution. Its physical implementation and
separation from the Java stack vary by JVM.

## 4. Stack vs Heap, References and Reachability

For `Employee emp = new Employee();`, conceptually the object is on the
heap and the local reference is in the current stack frame.

``` text
Java Stack                         Heap
+-------------------+             +----------------------+
| emp (reference)   |------------>| Employee object      |
+-------------------+             +----------------------+
```

-   Multiple references can point to the same object.
-   Reassigning one reference does not change another reference.
-   Instance fields receive default values (for example, an `int` field
    defaults to `0`).
-   Local variables must be definitely assigned before use.
-   Static fields are associated with the class and shared by its
    instances. Access through an object reference is legal, but using
    the class name is preferred.
-   `emp = null` does not immediately delete the object; it may make it
    eligible for GC if no other reachable reference points to it.
-   GC is based on **reachability from GC roots**, not simple reference
    counting.
-   Circularly linked objects can be collected if no GC root can reach
    them.

``` text
GC Root ---> A ---> B
               ^    |
               |____|

If no GC root reaches A or B, both are eligible for collection.
```

Examples of GC roots include references from active thread stacks,
relevant static references and JVM-internal roots.

**Implementation caveat:** optimizations such as escape analysis and
scalar replacement can change physical allocation behavior. Stack/heap
diagrams are a useful conceptual model, not a guarantee about every
allocation.

## 5. Class Loader Subsystem

A class loader loads class definitions into the JVM.

### Built-in class loaders

``` text
Bootstrap Class Loader
          |
          v
Platform Class Loader
          |
          v
Application Class Loader
```

-   **Bootstrap:** fundamental runtime classes such as
    `java.lang.Object`, `String` and `System`.
-   **Platform:** other platform classes. In Java 9+, Platform Class
    Loader replaced the old Extension Class Loader.
-   **Application:** application classes and dependencies available
    through the application class path/module configuration.

Examples: `java.lang.String` is normally loaded by Bootstrap; an
application class such as `com.example.hrms.EmployeeService` is normally
loaded by Application.

The module system and class-loader system are related but distinct; do
not assume each module has its own unique class loader.

### Parent Delegation Model

A class loader normally asks its parent to load a requested class first.
If the parent cannot load it, the child tries.

``` text
Application loader
       | delegates
       v
Platform loader
       | delegates
       v
Bootstrap loader
       |
       v
If parent cannot load, request returns down
the chain and a child may attempt loading.
```

This helps protect core Java classes from being replaced by application
classes and supports consistent class identity. Modern Java restricts
defining classes in protected packages such as `java.lang`.

## 6. Loading, Linking and Initialization

``` text
Loading
   |
   v
Linking
   +--> Verification
   +--> Preparation
   +--> Resolution
   |
   v
Initialization
```

-   **Loading:** JVM finds/reads the class representation and creates
    its runtime representation.
-   **Verification:** checks class-file structure and bytecode
    constraints, including type-safety rules. It is not a complete
    security system and does not prove code is harmless.
-   **Preparation:** allocates static fields and assigns default values.
    For example, a static `int` initially receives `0`.
-   **Resolution:** converts symbolic references into direct references
    as required; it may be lazy.
-   **Initialization:** executes explicit static field initializers and
    static blocks according to Java initialization rules.

Example:

``` java
class Demo {
    static int value = 10;
    static {
        value = 20;
    }
}
```

After initialization, `value` is `20`.

### Why verify bytecode if javac compiled it?

A `.class` file may have been produced by another compiler, generated or
modified by bytecode tools, obtained externally, or changed after
compilation. Verification checks JVM structural/type constraints. It
does not guarantee the program is harmless; valid code can still delete
files if it has permission.

## 7. Interpreter and JIT

-   **Interpreter:** executes bytecode instructions.
-   **JIT (Just-In-Time) compiler:** compiles frequently executed
    ("hot") code into native machine code and may apply runtime
    optimizations.

``` text
Java bytecode
      |
      v
 Interpreter ----> identify hot code
                         |
                         v
                    JIT compiler
                         |
                         v
                 Native machine code
```

-   Not every method is necessarily JIT-compiled.
-   Runtime profiling, hotness thresholds and heuristics influence
    compilation.
-   JIT can improve performance for frequently executed code.
-   JIT does not overwrite the `.class` file on disk.
-   The JVM can retain bytecode and use deoptimization/recompilation;
    compiled code is managed in a code cache.

## 8. Garbage Collection Fundamentals

GC reclaims heap memory occupied by objects that are no longer reachable
from GC roots. Eligibility does not mean immediate collection.

### Mark and Sweep

1.  Mark objects reachable from GC roots.
2.  Sweep/reclaim unmarked objects.
3.  Live objects are not necessarily moved, so free space can become
    fragmented.

``` text
Before: [Live A] [Dead] [Live B] [Dead] [Live C]
After:  [Live A] [Free] [Live B] [Free] [Live C]
```

### Mark and Compact

Marks live objects, reclaims dead objects, then moves survivors together
to reduce fragmentation.

``` text
Before: [Live A] [Free] [Live B] [Free] [Live C]
After:  [Live A] [Live B] [Live C] [   Free   ]
```

### Copying

Copies reachable objects from a source space into a destination space,
then reclaims the old source space. It reduces fragmentation but
requires destination capacity.

## 9. Generational Garbage Collection

### Generational Hypothesis

Most objects become unreachable soon after creation; a smaller
percentage survive for a long time. Generational GC uses this pattern to
manage short-lived and long-lived objects separately.

### Traditional generational layout

``` text
                 JVM HEAP
+--------------------------------------+
|           YOUNG GENERATION           |
|  +------------+  +------+ +------+   |
|  |    Eden    |  |  S0  | |  S1  |   |
|  +------------+  +------+ +------+   |
+--------------------------------------+
|            OLD GENERATION            |
+--------------------------------------+
```

This is a traditional layout used by collectors such as Parallel GC.
Some modern collectors organize memory differently.

### Eden

New objects are typically allocated in Eden in traditional generational
collectors.

### Survivor spaces S0 and S1

The two survivor spaces alternate as **From** and **To** spaces: - One
is the source; the other is the destination. - Reachable objects are
copied to the destination. - Unreachable objects are reclaimed. - The
old source space can be cleared and reused. - Roles switch in a later
collection.

``` text
Eden + From-Space
        |
        | copy reachable objects
        v
     To-Space

Unreachable objects are reclaimed.
Old From-Space becomes reusable.
```

Benefits: easy reclamation of dead objects, compact placement of
survivors, and tracking of object age.

### Promotion

Objects that survive enough Young GC cycles may be promoted to Old
Generation.

``` text
New object -> Eden -> Survivor space(s) -> Old Generation
```

Promotion is not based only on age. Collector policies may also consider
object size, survivor-space capacity and adaptive thresholds.

### Why generations help

Young objects are collected relatively frequently because many die
quickly. Long-lived objects are managed separately, avoiding the need to
treat the whole heap equally for every young collection.

## 10. Minor, Major and Full GC

Terminology varies by collector and tool; use careful wording.

-   **Minor GC / Young GC:** commonly means collection focused on Young
    Generation.
-   **Major GC:** commonly used for Old Generation collection, but usage
    is not universal.
-   **Full GC:** generally refers to a collection involving the entire
    heap; exact scope and work depend on the collector.

Do not assume every Major GC is a Full GC, or that every Full GC has
identical pause behavior.

Examples: - Eden is nearly full and has dead objects → a Young/Minor GC
is generally appropriate. - Old Generation needs reclamation → an
old-generation collection (often called Major GC) may occur. - A
collection involving the entire heap → commonly called Full GC.
